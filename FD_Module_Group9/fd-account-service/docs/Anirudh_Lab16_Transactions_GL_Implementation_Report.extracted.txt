2. Objective and Scope
2.1 Objective
Lab 16 extends Fixed Deposit (FD) account creation so that every new FD starts its life with a recorded financial transaction. The Lab Manual (L16 §1) states the objective as:
Automated recording of the initial deposit transaction during account creation.
Ensuring the transaction history is initialized properly for future auditing and reporting.
Associating the FD account with a transaction lifecycle right from creation.
L16 §2 adds that the initial DEPOSIT establishes the opening balance and links the account to the general ledger, capturing audit metadata: who created the account, when, and for what amount.

6.3 DDL (from the final script)
sql/l16_fd_transactions.sql
CREATE TABLE IF NOT EXISTS fd_transactions (
    txn_id             BIGINT        NOT NULL AUTO_INCREMENT,
    fd_account_no      VARCHAR(20)   NOT NULL,
    txn_type           VARCHAR(20)   NOT NULL,   -- DEPOSIT (L16); WITHDRAWAL / INTEREST / MATURITY_PAYOUT etc. per Lab Manual
    amount             DECIMAL(18,2) NOT NULL,
    currency           VARCHAR(3)    NULL,       -- copied from fd_accounts.currency
    debit_gl_account   VARCHAR(50)   NOT NULL,   -- double entry: debit leg (see GLAccounts.java)
    credit_gl_account  VARCHAR(50)   NOT NULL,   -- double entry: credit leg
    status             VARCHAR(20)   NOT NULL,   -- POSTED for committed entries
    txn_timestamp      TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    remarks            VARCHAR(500)  NULL,
    uuid               VARCHAR(255)  NOT NULL,
    created_by         VARCHAR(50)   NULL,       -- authenticated user who triggered the event
    created_at         TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_by         VARCHAR(50)   NULL,       -- in team ER; never set (ledger is append-only)
 
    -- Technical guard (not a business field): holds fd_account_no only for
    -- DEPOSIT rows, NULL otherwise. The unique key below therefore allows at
    -- most ONE initial DEPOSIT per FD account at database level, while any
    -- number of other transaction types remain allowed.
    deposit_guard      VARCHAR(20) GENERATED ALWAYS AS
                       (CASE WHEN txn_type = 'DEPOSIT' THEN fd_account_no ELSE NULL END) STORED,
 
    PRIMARY KEY (txn_id),
    UNIQUE KEY uk_fd_txn_uuid (uuid),
    UNIQUE KEY uk_fd_txn_one_deposit (deposit_guard),
    KEY idx_fd_txn_account_time (fd_account_no, txn_timestamp),
    -- Default RESTRICT actions: MySQL forbids CASCADE/SET NULL on base
    -- columns of a stored generated column, and a ledger must never cascade.
    CONSTRAINT fk_fd_txn_account FOREIGN KEY (fd_account_no)
        REFERENCES fd_accounts (fd_account_no),
    CONSTRAINT chk_fd_txn_amount_non_negative CHECK (amount >= 0)
);

public FDTransaction(String fdAccountNo, String txnType, BigDecimal amount, String currency,
                     String debitGlAccount, String creditGlAccount, String remarks, String createdBy) {
    this.fdAccountNo = fdAccountNo;
    this.txnType = txnType;
    this.amount = amount;
    this.currency = currency;
    this.debitGlAccount = debitGlAccount;
    this.creditGlAccount = creditGlAccount;
    this.remarks = remarks;

@PrePersist
void prePersist() {
    LocalDateTime now = LocalDateTime.now();
    if (txnTimestamp == null) txnTimestamp = now;
    if (createdAt == null) createdAt = now;
    if (uuid == null) uuid = UUID.randomUUID().toString();
    if (status == null) status = STATUS_POSTED;
}

8. Automatic Initial DEPOSIT Logging
What: when an FD is created through create-with-txn, a DEPOSIT row is written to fd_transactions automatically. Why: Lab Manual L16 §1–§3 requires the initial deposit to be recorded during account creation so that the account has a transaction history from day one. How: recordInitialDeposit builds the row from the saved FixedDepositAccount, not from the raw request, so the ledger always matches what was stored.
FDTransactionService.recordInitialDeposit
@Transactional(propagation = Propagation.MANDATORY)
public FDTransaction recordInitialDeposit(FixedDepositAccount fd, String createdBy) {
    return transactionRepository
            .findFirstByFdAccountNoAndTxnTypeOrderByTxnIdAsc(fd.getFdAccountNo(), FDTransaction.TYPE_DEPOSIT)
            .orElseGet(() -> transactionRepository.save(new FDTransaction(
                    fd.getFdAccountNo(),
                    FDTransaction.TYPE_DEPOSIT,
                    fd.getPrincipalAmount(),
                    fd.getCurrency(),
                    GLAccounts.ASSET_CUSTOMER_REMITTANCE,
                    GLAccounts.LIABILITY_FD_DEPOSITS,
                    INITIAL_DEPOSIT_REMARKS,
                    createdBy)));
}

9. Integration with FD Account Creation
Lab 16 reuses the L13 creation logic instead of copying or modifying it. createFDAccountWithTransaction calls FDAccountService.create(...), so customer, product, term, minimum-deposit and rate validation and account-number generation behave exactly as in Vritika's code. No L12/L13 source file was modified (verified by checksum comparison against the original project).
FDTransactionService.createFDAccountWithTransaction
@Transactional
public FDAccountCreationResponse createFDAccountWithTransaction(FDAccountRequest request, String createdBy) {
    FDAccountResponse created = fdAccountService.create(request, createdBy);
 
    // Write the pending fd_accounts INSERT now so the fd_transactions foreign key is satisfied
    // and any account-level constraint error surfaces before the ledger row is written.
    fdRepository.flush();
 
    FixedDepositAccount fd = fdRepository.findById(created.fdAccountNo())
            .orElseThrow(() -> new IllegalStateException(
                    "FD account not found after creation: " + created.fdAccountNo()));
 
    FDTransaction deposit = recordInitialDeposit(fd, createdBy);
 
    return new FDAccountCreationResponse(
            fd.getFdAccountNo(),
            deposit.getTxnId(),
            CREATION_MESSAGE,
            transactionHistoryUrl(fd.getFdAccountNo()));
}
9.1 Why each step is there
Step | Why
fdAccountService.create(request, createdBy) | Single source of truth for L13 rules; joins the outer transaction (both use REQUIRED).
fdRepository.flush() | Executes the pending fd_accounts INSERT before the ledger INSERT so the foreign key is always satisfied, and surfaces account-level constraint errors early.
fdRepository.findById(...) | Loads the managed, saved entity so the ledger row uses stored values (principal, currency).
recordInitialDeposit(fd, createdBy) | Writes the DEPOSIT and GL legs in the same transaction.
return FDAccountCreationResponse | Lab Manual L16 §6.2 response plus history link.

10.3 How the GL entry is stored and associated
The team ER has no GL master table; GL accounts are VARCHAR(50) codes on each fd_transactions row (debit_gl_account, credit_gl_account).
One row therefore is one balanced double entry: one amount, debited from one account and credited to another. Debits always equal credits by construction.
The GL entry and the FD transaction are the same record, sharing txn_id, uuid, fd_account_no and txn_timestamp; no separate link is needed.
GLAccounts is a shared team contract: later postings must reuse these codes (e.g. L19 maturity payout debits LIABILITY_FD_DEPOSITS).
Scope note:  only the DEPOSIT mapping is implemented. Interest, withdrawal, penalty and maturity GL entries belong to other team members (Section 21).
11. Transaction Atomicity and Rollback
[Lab Manual] L16 §3 requires both records to be saved in a single database transaction. The transaction boundary is FDTransactionService.createFDAccountWithTransaction.
Method | Annotation | Behaviour
FDTransactionService.createFDAccountWithTransaction | @Transactional | Starts the transaction (boundary)
FDAccountService.create (L13) | @Transactional | Joins (REQUIRED)
FDTransactionService.recordInitialDeposit | @Transactional(propagation = MANDATORY) | Joins; throws IllegalTransactionStateException if called with no transaction

Spring rolls back on any RuntimeException. All L13 validation failures are IllegalArgumentException, so a rejected request leaves no fd_accounts row and no fd_transactions row.
11.1 Error handling
Situation | Handled by | HTTP result
Missing/invalid request fields (@Valid) | ApiExceptionHandler.validation | 400 with field errors map
Business rule (customer, product, term, minimum deposit) | L13 IllegalArgumentException → ApiExceptionHandler.badRequest | 400 {"status":"error","message":...}, full rollback
History for unknown account | getTransactions throws IllegalArgumentException | 400 "FD account not found: …"
Wrong role | @PreAuthorize | 403
No credentials | Spring Security HTTP Basic | 401
DB constraint violation at commit | not mapped by ApiExceptionHandler | 500 (rollback still correct) — see Section 20

12. Duplicate Prevention and Idempotency
A financial operation must not create duplicate entries when repeated. Three layers protect the initial DEPOSIT:
Layer | Mechanism | Basis
Application | recordInitialDeposit first calls findFirstByFdAccountNoAndTxnTypeOrderByTxnIdAsc(no, "DEPOSIT"); if a DEPOSIT exists it is returned and nothing is written. | Industry practice
Database | deposit_guard = fd_account_no only when txn_type = 'DEPOSIT'; UNIQUE KEY uk_fd_txn_one_deposit. A second DEPOSIT for the same account is rejected even if the service is bypassed. Other types are unaffected because NULLs are not compared. | Industry practice
Transaction contract | Propagation.MANDATORY prevents the deposit being written outside the account-creation transaction. | Industry practice

sql/l16_fd_transactions.sql — database guard
deposit_guard VARCHAR(20) GENERATED ALWAYS AS
              (CASE WHEN txn_type = 'DEPOSIT' THEN fd_account_no ELSE NULL END) STORED,
UNIQUE KEY uk_fd_txn_one_deposit (deposit_guard),
12.1 Evidence
Test recordInitialDeposit_calledAgain_returnsExistingDepositAndWritesNothing — PASSED (same txn_id returned, row count stays 1).
Test recordInitialDeposit_outsideATransaction_isRejected — PASSED.
MySQL: manual second DEPOSIT insert for BR0010000016 failed with ERROR 1062 (23000) … Duplicate entry 'BR0010000016' for key 'fd_transactions.uk_fd_txn_one_deposit'; rows afterwards: 1.
Not guaranteed:  if a client re-submits the whole create-with-txn request (e.g. after a timeout), L13 generates a new account number, so a second FD with its own DEPOSIT is created. Preventing this needs a client idempotency key in FDAccountRequest, which is the L13 contract. "Exactly once" is therefore not claimed.

15. Transaction History Integration
The history endpoint is the target of the success link and the place where every later transaction type (withdrawal, interest, maturity) will appear automatically once teammates insert into fd_transactions.
controller/FDTransactionController.java — history endpoint
@GetMapping("/{fdAccountNo}/transactions")
@PreAuthorize("hasAnyRole('BANK_OFFICER','ADMIN','CUSTOMER')")
public ResponseEntity<List<FDTransactionResponse>> getTransactions(@PathVariable String fdAccountNo) {
    return ResponseEntity.ok(fdTransactionService.getTransactions(fdAccountNo));
}
FDTransactionService.getTransactions
@Transactional(readOnly = true)
public List<FDTransactionResponse> getTransactions(String fdAccountNo) {
    if (!fdRepository.existsById(fdAccountNo)) {
        throw new IllegalArgumentException("FD account not found: " + fdAccountNo);
    }
    return transactionRepository.findByFdAccountNoOrderByTxnTimestampAscTxnIdAsc(fdAccountNo)
            .stream()
            .map(FDTransactionResponse::from)
            .toList();
}
Ordering: txn_timestamp ascending, then txn_id (stable for same-timestamp rows).
Scoping: only rows for the requested account (test history_isScopedToTheRequestedAccount — PASSED).
Roles: same as the existing GET /api/fd/account/{fdAccountNo} (BANK_OFFICER, ADMIN, CUSTOMER).
Unknown account: HTTP 400, consistent with the existing L13 getById behaviour.
Actual MySQL result: one item — DEPOSIT, 200000.00, ASSET_CUSTOMER_REMITTANCE → LIABILITY_FD_DEPOSITS, POSTED, txnId 1.
Gap:  Lab Manual L12 §5 says customers may view only their own FD records. No per-customer ownership check is applied (the in-memory HTTP Basic users are not linked to a customer_id; the existing L13 GET has the same gap). See Section 20.

24. Conclusion
Lab 16 is implemented on top of Vritika's L12/L13 FD module without modifying any of her classes. Creating an FD through POST /api/fd/account/create-with-txn now records an initial DEPOSIT in the new append-only fd_transactions ledger, in the same database transaction as the account, with a balanced debit/credit GL entry and audit metadata. The response returns the FD account number, the initial transaction ID and a link to the account's transaction history.
All 21 automated tests passed, and a MySQL end-to-end run confirmed the contract, role restrictions, rollback, and the database-level duplicate guard. The one failed check (/health requiring login) is a pre-existing L12/L13 configuration issue.
Open items are the Angular success UI (no frontend exists in the project), team-lead confirmation of task ownership and of the schema choice, the customer-ownership check on history, and request-level idempotency. These are documented in Sections 14, 20 and 22 so the next developer can complete them.
